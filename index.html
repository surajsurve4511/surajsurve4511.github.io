6-DOF AI Robotic Arm — Bridging LLM Intent with Physical Kinematics

● ACTIVE
RoboticsAI/ML Generative AIHardware

Building a robotic arm is standard. Building an arm that translates plain English — "pick the red cube" — into sub-centimeter, collision-free physical movement while maintaining a real-time Digital Twin is an architectural nightmare. Here is how I built the bridge between natural language hallucination and precise physical kinematics.

⚠ Bottleneck 01 — The Translation Gap

LLMs generate text. Servo motors require joint angles.

The Problem: There is no native path from a language model's probabilistic output to the deterministic joint-angle commands a 6-DOF arm requires.

The Engine: I engineered a "Brain Node" — an Ollama local LLM extracts spatial intent and object description → YOLO World vision pipeline locates the object in the live camera feed → 3D coordinates are computed → ROS2 MoveIt calculates inverse kinematics and a collision-free trajectory → physical execution.

⚠ Bottleneck 02 — Single-Camera Depth Failure

One camera cannot map 3D space for sub-centimeter accuracy.

The Problem: A monocular camera provides 2D projections. Sub-centimeter pick-and-place accuracy requires true 3D spatial understanding.

The Engine: Dual-camera spatial mapping (base-mounted + tabletop). Fixed reference mat calibration with YOLO World auto-recognizing reference points — fusing both feeds for absolute 3D object coordinates without manual annotation.

⚠ Bottleneck 03 — Sim-to-Real Synchronization

Untested AI code destroys servo motors.

The Problem: Testing experimental motion planning algorithms on physical hardware risks burning out ₹8,000+ servo motors.

The Engine: Bidirectional Digital Twin using Gazebo. Every physical movement mirrors in simulation. Every untested algorithm is validated in the Twin before being pushed to the ESP32/Arduino controllers.

⚠ Bottleneck 01 — Apple Guideline 5.1.1 Account Deletion

Apple demands full account deletion. Your data spans 10+ tables.

The Problem: App Store compliance requires complete user data erasure — but user data is scattered across profiles, gardens, care logs, diagnoses, streaks, badges, credits, reminders, and subscriptions.

The Engine: 13-step cascading deletion flow cleaning all data across 10+ tables, culminating in a PL/pgSQL security-definer RPC that removes the user from Supabase auth.users. Explicit cache clearing prevents premium status from bleeding between accounts.

⚠ Bottleneck 02 — API Key Security in Mobile APKs

Every APK can be decompiled. Your API keys are exposed.

The Problem: Bundling API keys in mobile builds is a security vulnerability — anyone can extract them from the APK.

The Engine: All sensitive keys stored in a Supabase app_config table, fetched at runtime behind RLS policies. Zero secrets in the build artifact. Runtime key rotation without app updates.

⚠ Bottleneck 01 — Recipe Engine Atomic Deduction

Every POS order must deduct ingredients without partial failures.

The Problem: A single order can contain multiple dishes, each with multiple ingredients. If the inventory update fails mid-transaction, stock counts become permanently inconsistent.

The Engine: On every POS order — query dish_ingredients, compute qty_per_portion × order_qty, batch-update mess_inventory, insert to inventory_txns — all within a single atomic transaction with BEGIN/COMMIT/ROLLBACK.

⚠ Bottleneck 02 — Multi-Tenant Data Isolation

21 API modules. Zero cross-organization data leakage.

The Problem: In a multi-tenant SaaS, every single query across every single route must be scoped to the correct organization. One missed filter = data breach.

The Engine: JWT-scoped org_id filtering enforced at the middleware level across all 21 route modules. Supabase RLS policies as a second defense layer for customer-facing QR ordering endpoints.
